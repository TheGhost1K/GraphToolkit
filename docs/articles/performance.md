> [!NOTE]
> В колонке «Время» для итеративных алгоритмов с приоритетной очередью
> используется бинарная куча (`PriorityQueue` из .NET 6+).
> Для графов с целочисленными весами и ограниченным диапазоном можно
> ускорить до O(V + E) через bucket queue — в библиотеке не реализовано.

## Практические рекомендации

### Выбор структуры данных

| Случай | Реализация | Почему |
|---|---|---|
| Разреженный граф (E ≈ V) | `Graph<T>` | Память O(V + E), обход соседей O(deg) |
| Плотный граф (E ≈ V²) | `AdjacencyMatrixGraph<T>` | Проверка ребра O(1) |
| Нужны частые `HasEdge` / `GetWeight` | `AdjacencyMatrixGraph<T>` | O(1) вместо O(deg) |
| Нужен `Neighbors` в горячем цикле | `Graph<T>` | O(deg) вместо O(V) |
| Фиксированный размер V ≤ 5000 | Любая | Разница несущественна |
| V > 10⁴ | `Graph<T>` | Матрица займёт слишком много памяти |
| Динамически меняющийся | `Graph<T>` | Не требует перевыделения матрицы |

**Правило выбора:**

```
E > V² / 4 ?
├─ Да → AdjacencyMatrixGraph<T>
└─ Нет → Graph<T>
```

Например, граф на 1000 вершин:
- `Graph<T>` выгоден, если E < 250 000 (разреженный)
- `AdjacencyMatrixGraph<T>` выгоден, если E > 250 000 (плотный)

> приближённые алгоритмы или декомпозицию.

### Оптимизации

1. **Избегайте LINQ в горячих циклах** — `foreach` вместо `.Where()`
2. **`PriorityQueue`** — встроенный класс из .NET 6+, не пишите свою кучу
3. **Struct-based edges** для V > 10⁶ (замена класса на struct)
4. **`ArrayPool<T>`** — для временных массивов в `Dinic`, `FloydWarshall`
5. **Кэшируйте `Neighbors`** в локальной переменной, если вызываете в цикле
6. **Матрица смежности для плотных графов** — O(1) проверка ребра
7. **Параллелизация** — Борувка, level-synchronous BFS, строки матрицы Флойда
8. **Bucket queue** вместо бинарной кучи для целочисленных весов
9. **Хеш-множества** `HashSet<T>` вместо `List<T>` для `visited`
10. **`AggressiveInlining`** на маленьких горячих методах (`[MethodImpl]`)

### Что НЕ оптимизировать раньше времени

- **Замена `Dictionary` на кастомную хеш-таблицу** — редко даёт > 10%
- **Struct вместо class для `Edge<T>`** — если V < 10⁵, разница незначительна
- **Свои аллокаторы** — почти никогда не нужны
- **SIMD в графовых алгоритмах** — применимо только к Флойду, эффект мал

Сначала **измерьте** (`BenchmarkDotNet`, `Stopwatch`), потом оптимизируйте.

### Пример микрооптимизации

```csharp
// Медленно: LINQ в горячем цикле
foreach (var e in graph.Neighbors(u).Where(x => x.Weight > 0)) { ... }

// Быстро: обычный foreach
foreach (var e in graph.Neighbors(u))
{
    if (e.Weight <= 0) continue;
    // ...
}
```
